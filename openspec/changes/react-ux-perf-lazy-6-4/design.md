# Design

## Context

См. `proposal.md` (Why). Ниже — наблюдаемое состояние кода, от которого отталкивается подход.

Settings и chat смонтированы всегда и переключаются через `<Activity mode="visible|hidden">` в `react-app/src/pages/main/ui/main.tsx`. У `Activity` скрытие снимает effects и при повторном показе запускает их снова; state Redux при этом жив. Флаг `elements` (в том числе `manageModelsPopup`) входит в persist whitelist.

`Settings` всегда рендерит `<ManageModels>`, даже когда попап закрыт (`settings.tsx`). В `manage-models.tsx` effect при `isOpened` делает `dispatch(fetchCatalog({ forceRefresh: true }))` и зависит от `providerUrl`. Пока `isOpened === false`, запрос из этого effect не уходит. Тяжёлая работа на открытии settings — само дерево: `displayModels` собирает все `ModelItem` и отдаёт их в `Popup`, который кладёт children в DOM и при закрытом попапе (`visibility: hidden`, не размонтирование). `fetchInstalledModels` в `model-ipc-slice.ts` объявлен и не имеет вызывающих мест; installed-состояние списка берётся из тегов каталога. После install/remove thunk сам делает `fetchCatalog({ forceRefresh: true })` с `id`/`url` из settings — это явное обновление, его сохраняем.

`Popup` (`popup.scss`) анимирует open/close `transition: all 0.28s`. `enableLazyLoading` включает обёртку `LazyListItem` только если children уже массив длиннее порога (у manage-models порог 20). Родитель при этом создаёт весь массив `ModelItem` в одном коммите. `LazyListItem` после видимости вызывает `getBoundingClientRect` в `onVisible` — синхронный layout. `popupRef` в `Popup` создаётся через `createRef` на каждом рендере.

Chat: `ChatSidebar` монтируется только при `showSidebar`. Список — полный `.map` `SelectorOption`, у строки вызывается `splittingContentOfModel`. `ChatMessages` тоже монтирует все `MessageBubble`; флаг `isVisible || index >= length - 10` не отменяет создание узлов. `loadChats` на эффекте `Chat` и `loadChat` при выборе чата остаются загрузкой данных CRUD, их контракт не трогаем.

Порядок этапа: 6.1 → 6.2 → 6.3 → **6.4** → 7.1. Rust-слои этот change не расширяет.

## Goals / Non-Goals

**Goals:**

- Settings открывается без каталожного запроса и без дерева manage-models до клика «manage models».
- Кэш каталога ключуется provider id + `url`; тяжёлый refresh — при пустом/негодном ключе, смене url и после install/remove.
- Один хук порционного раскрытия обслуживает popup и chat.
- Длинный каталог и длинные chat-списки не коммитятся одним кадром; оболочка попапа опережает список.
- Три оптимизации применяются по очереди с остановкой на ручной тест.

**Non-Goals:**

- Удаление Electron и правка core/hosts.
- Снятие `TODO(rag)` / `TODO(splash)`, возврат Embedded, облачные адаптеры.
- Новая библиотека виртуализации и перекладка FSD.
- Откладывать `loadChats` / `loadChat` / generate как «оптимизацию данных».

## Decisions

### 1. Тяжёлый manage-models монтируется только с открытым попапом

`Settings` рендерит `ManageModels` при `manageModelsPopup === open`. Закрытый попап не держит список `ModelItem` в скрытом DOM.

Уход с секции settings (Activity → hidden) закрывает `manageModelsPopup`. Иначе persist флага снова поднимет список и `forceRefresh` на следующем заходе в settings, и checkpoint оптимизации 1 будет измерять попап, а не экран настроек.

Альтернатива — оставить компонент смонтированным и обнулять children. Effects и селекторы каталога всё равно крутятся на каждом показе settings. Размонтирование дешевле; снимок каталога лежит в Redux и переживёт unmount.

### 2. Кэш каталога по паре (provider id, url)

При открытии попапа:

- нет снимка или ключ снимка отличается от текущего id+url → `fetchCatalog` с `forceRefresh: true` (чужой Ollama не показываем);
- ключ совпадает → отдать кэш, без `forceRefresh` только из-за повторного open;
- install/remove по-прежнему сами диспатчат `forceRefresh` после мутации.

Запросы по-прежнему берут `id` и `url` из provider settings через существующий путь thunk → `BackendClient`. Смена url в форме, пока попап закрыт, запрос не запускает: инвалидация случится на следующем открытии по ключу.

`fetchInstalledModels` на mount settings не подключать.

Альтернатива — оставить `forceRefresh: true` на каждый open. Это как раз тяжёлый sync, от которого атомы 6.4 уходит на повторных заходах, и он не нужен, пока url тот же.

### 3. Хук `useProgressiveReveal`, список после анимации открытия

Имя: `useProgressiveReveal`. Место: `react-app/src/shared/lib/hooks/use-progressive-reveal/` (рядом с `use-intersection-observer`, чтобы popup и chat импортировали shared, а не виджеты друг друга).

Контракт хука:

- вход: список элементов, флаг «пора раскрывать», `chunkSize` (старт 20 — текущий `lazyLoadingThreshold`), режим отложения `defer: 'transitionend' | 'frame'`;
- выход: уже раскрытый префикс, флаг готовности оболочки, сброс префикса при закрытии/смене списка.

Для popup режим по умолчанию — `transitionend` на корне `.popup` (CSS 280ms). Если событие не пришло (переход прерван), fallback-таймер 280ms, затем первый chunk. Дальше порции через `requestAnimationFrame` / `requestIdleCallback`, где idle есть, иначе следующий кадр. Закрытие сбрасывает префикс, чтобы close не раскладывал ещё не смонтированный хвост.

`Popup` / `PopupWithSearch` при `enableLazyLoading` и длинном списке отдают в DOM только префикс хука. `LazyListItem` остаётся тонкой обёрткой видимой порции (placeholder высоты строки). Из `onVisible` убрать синхронный `getBoundingClientRect`, если колбэк не нужен вызывающему коду. `createRef` в `Popup` заменить на `useRef`, чтобы focus-effect не переподписывался каждый рендер.

Короткие popup’ы (язык, провайдер) порог не переходят и идут текущим путём без отложения.

Альтернатива — только IntersectionObserver, без ожидания transition. Она уже в коде и не мешает родителю создать все children до observer. Альтернатива — подключить react-window/virtua. Это новая зависимость и смена UX скролла шире, чем атом просит.

Если ручной тест оптимизации 2 покажет, что пустая оболочка 280ms хуже, чем порции во время анимации, у того же хука переключается `defer` на `frame` (первый chunk на следующем кадре, без ожидания `transitionend`). Спека при этом та же: весь каталог не в кадре открытия. Новый change для этой подстройки не нужен.

### 4. Chat подключает тот же хук к sidebar и к старым сообщениям

Профилирование по коду (без отдельного прохода «исследовать» на apply):

- jank открытия sidebar — полный map в `chat-sidebar.tsx` плюс разбор контента строки. Хук с `defer: 'frame'` на `filteredChats`: первый экран сразу, хвост порциями. Поиск по-прежнему фильтрует полный массив данных в памяти (это дёшево относительно DOM) и заново раскрывает видимый префикс.
- jank переключения чата — полный map в `chat-messages.tsx`. Последние 10 сообщений и стриминговый bubble монтируются сразу (как сейчас задумано условием хвоста). Более старые идут через `useProgressiveReveal` вверх по истории. `scrollToBottom`, ResizeObserver и автоскролл генерации остаются на контейнере и хвосте.
- `chat.tsx` не переписывать: `loadChats` при показе секции и `loadChat` при выборе остаются. Sidebar по-прежнему условный по `showSidebar`.

Альтернатива — виртуализировать оба списка отдельными компонентами. Общий хук это закрывает без второго механизма.

### 5. Apply останавливается после каждой оптимизации

Оптимизации 1, 2 и 3 — отдельные группы в `tasks.md`. После группы агент пишет «готово к ручному тесту» и не начинает следующую, пока пользователь не подтвердил. Опровержение чинит ту же группу. Чекбокс подтверждения ставит только пользователь (в артефакте он остаётся неотмеченным со стороны агента).

Порядок внутри атома совпадает с планом: settings → popup + хук → chat на этом хуке. Оптимизация 3 не начинается, пока хука нет.

### 6. Проверки без rust

Юнит-тест хука: порции растут по chunk, при `open === false` префикс пуст, смена ключа списка сбрасывает префикс. Существующие тесты `BackendClient` / chat-ipc прогнать, если их задевает diff; контракт клиента не менять. `cargo test` не входит в DoD: core не трогаем. Если в ходе оптимизации 1 обнаружится, что fetch всё же нужен на settings по причине вне UI (такого вызова сейчас нет), это фиксируется в комментарии к задаче до обхода, а не молчаливым запросом.

## Risks / Trade-offs

- [Пользователь уходит с settings с открытым попапом] → закрытие секции гасит `manageModelsPopup`; список не восстанет из persist на следующем заходе.
- [`transitionend` не срабатывает] → fallback 280ms, первый chunk всё равно появляется.
- [Пустая оболочка 280ms ощущается как лаг] → переключить `defer` на `frame` в том же хуке после опровержения checkpoint 2.
- [Кэш каталога устарел без смены url (модель поставили снаружи UI)] → install/remove внутри UI обновляют снимок; внешнее изменение до следующего явного refresh не подхватится. Явная кнопка «обновить» вне скоупа, пока checkpoint не попросит её как фикс того же N.
- [Порции истории сдвигают scroll] → хвост из 10 сообщений и стрим монтируются сразу; догрузка старых идёт выше viewport, якорь скролла — низ контейнера.
- [Скрытие Activity повторно гоняет effects] → catalog effect живёт только в смонтированном по открытому флагу `ManageModels`.

## Migration Plan

Миграции данных нет. Каталог — runtime-снимок в Redux, не persist. Откат — вернуть прежний mount `ManageModels` и прямой `.map` в popup/chat; хук можно оставить неиспользуемым только вместе с откатом call sites, отдельным коммитом отката всего атома.

Выкладка совпадает с обычным фронтом dual-mode (тот же `react-app` для Tauri и HTTP). Отдельный feature-flag не вводим: поведение включается кодом оптимизаций по мере confirm.

## Open Questions

Нет. Размер порции (20) и режим `defer` для попапа (`transitionend`) заданы выше; подстройка по симптомам ручного теста остаётся внутри той же оптимизации.
